## 三、仍然落后 / 未做的（照实写）

1. **没有公开索引 / 托管方 / 第三方 witness**。机制侧已补齐：只增台账、签名树头 STH、可移植公开索引件、链头公开披露；仍缺"公开托管 + 持续监视 + 独立 witness"，这需要域名/运维/第三方参与，属决策与外部动作。
2. **OCSP 覆盖不完整**。只对令牌链前两张证书查了 OCSP（GOOD、签名验过），根证书无 OCSP（正常）；且 OCSP 是"查询时刻"状态，长期验证需在 `nextUpdate` 到期前再查并留存。
3. **仍无见证人回执**。见证工具包已就绪（9 项待见证值、逐项核法、回执模板、只增回执台账），但见证本身必须由真人/机构完成——这一步无法用代码替代，只能由你去约人。
4. **身份绑定是"自持密钥级"，不是 DID/VC**。已建 Ed25519 主张签名并把签名本身也上链，能证"持私钥者做了该主张且不否认"；但姓名与真实主体的映射仍靠外部凭据（GitHub 账号、公司注册、公证）交叉印证，尚无 W3C DID/VC 或企业 CA 身份背书。
5. **Apple 根不在 certifi，且官方渠道取不到**（403），故 Apple 令牌只作"链完整"的冗余旁证，不计入公共根；Windows 系统根存储亦无该根。已明确不引入第三方镜像证书凑数。

## 四、与标准的对应关系

- IETF `draft-fassbender-scitt-time-anchor`：把"RFC3161 依赖机构、机构可消失"作为结构性问题，主张以比特币账本纳入作为时间证明；并要求 Proof Bundle 内含 `.ots` 与 `claimed_hash`、验证方自行重算哈希。→ 本项目 `anchor_confirm.py` 正是"自行重算 + 双源核对"，`ANCHORS.json` 里保留了 heights/merkle root 供复核。
- IETF `draft-schrock-ep-evidence-record`：要求 RFC3161 令牌 **fail-closed** 验（解析、imprint 必须等于持有方独立计算的摘要、签名须验）；并强调"记录年龄不应退化为信任运营者自己的时钟"。→ `tsa_verify.py` 的 `verified` 字段就是四项与门，任一失败即 false。
- IETF `draft-ailex-vap-legal-ai-provenance`：Evidence Pack = manifest + events + anchors + merkle + keys + signatures，打包为 zip。→ `make_pack.py` 按同构组织（manifest 逐文件 sha256、锚证据同包、内附复验脚本与边界说明）。
- Sigstore Rekor：append-only + Signed Tree Head + 时间戳，且明确"日志必须被监控"才有长期信任。→ 我们的 `ANCHOR_LOG_CHAIN.json` 是弱化版（本地链头），差距在第 3 节第 1 条。

第三轮两个攻击点都不是"改代码能根治"的，属"机制边界必须说清"的类型，因此处置方式是**收紧措辞并公开披露链头**，而不是假装解决。

必须说清楚：**CA 被入侵这件事无法被任何本地机制"证明不存在"**。我们能做的是"可检测 + 可响应 + 留痕"，不是"已消除"。这一条从"未完成项"改判为"已声明并已建检测机制的边界项"，不当成已完成项粉饰。

**为什么没有去凑第 3 家公共根**：Apple TSA 令牌链是完整的（3 跳到 Apple Root CA 自签根），但该根不在 certifi，Apple 官网取根返回 403，Windows 系统根存储也没有它。技术上可以从 GitHub 第三方镜像拿到一份同名证书来"凑齐"——但那样等于引入一个**来源可疑的根**，用弱环节换取数字好看，是净损失。因此改为：
- 阈值语义按"**独立公共 CA 数 + 去中心锚**"定义（≥2 达标），不是按"TSA 总数"；
- 当前 2 家公共根（DigiCert、Certum）+ Apple 链完整但根非审计 + freetsa 社区自签 + 3 家 calendar + 比特币三区块锚，五条独立轨；
- 如果日后需要第 3 家公共根，正确路径是接一家公开审计 TSA（如 Sectigo/SSL.com，需解决端点可用性），而不是拿镜像证书。

## 十六、见证入口做成流水线：模板会刷新、回执会被机器初核、台账只增

前几轮一直说"见证回执 0 条，要人"。这一轮把"要不要人"之外的部分全做成机制，人只剩签字动作。

### 16.1 先修一个会害死见证人的隐患：模板过期

`out/WITNESS_RECEIPT_TEMPLATE.json` 里原来留着**旧值**：主张签名字节 sha256 写的是 `3b7ee668…`，日志链头写的是 `410d0894…`——与当前 `8012c494…` / `9abd56ef…` 不一致。任何见证人照旧模板核对，都会得出"对不上"，等于我们自己制造假阴性。

修法：新增 `make_witness_template.py`，每次发布前从 `IP_VERIFY/CLAIM_ANCHOR/LOG_ANCHOR/INDEX_LEDGER/TSA/ANCHORS/CLAIM_VERIFY` 现算一遍重生成；CI 加一步死锁：**模板里的根值必须等于 `index.json` 的根值**，不等就红。

### 16.2 回执收进来也不再靠人拍脑袋：`ingest_witness.py`

收一份回执按五步核：

1. **结构**：见证人名称、独立性声明、`public_url` 三者缺一即拒（没有公开地址的回执不可被引用）；
2. **数值**：回执的 `value_claimed` 必须等于本机当前承诺值，用旧数值一律拒；
3. **自算**：填了 `value_recomputed` 的，必须与 claimed 相等且 `match=true`；
4. **区块双源**：把高度拿去 `blockstream.info` 与 `mempool.space` 各查一次，两源一致且与回执 claimed 相符才算数；
5. **登记**：通过则写 `WITNESS_LEDGER.jsonl`（seq / 回执 canonical sha256 / prev_entry_hash / entry_hash），只增不改。

实测两条：正样本（自测回执，`--dry-run`）→ `MATCH`、`ledger_appended=false`、台账仍 0 字节；负样本（把根值改成 64 个 0）→ 退出码 1、`MISMATCH`，理由写"claimed 与本机当前值不一致：文件集合 Merkle 根"。

自测回执不冒充第三方：脚本检测 `self-test` 字样，未加 `--allow-self-test` 时拒绝登记；台账里的见证数仍按"非自测"计，目前依旧是 **0**。

### 16.3 入口：Issue 表单

`.github/ISSUE_TEMPLATE/witness-receipt.yml`：字段含名称、独立性声明、核对时间、回执 JSON（按模板）、公开链接、执行过的命令、两项强制勾选（"本人独立核对"+"只担保数值、不背书内容"）。任何人开一个 Issue 就是一份可引用的回执。
## 十七、第三与第四家公共根 TSA（2026-11-26 晚）

起因是自陈差距：四家 TSA 里只有 DigiCert、Certum 的链顶落在公共根，另外两家（Apple、freetsa）只算"链完整"的旁证。这一节把它补掉。

### 17.1 技术卡点不是网络，是解析器

第一版探测脚本 import 失败：`rfc3161_client` 里没有 `TimeStampRequestBuilder`，真实符号是 `TimestampRequestBuilder`，并且请求对象要 `.as_bytes()` 才能当 body。改用真实 API 后，Sectigo 与 GlobalSign 都返回 `granted`，但 Rust 侧解码器报 `ASN.1 parse error: InvalidSetOrdering`——两家令牌的 SET OF 排序不符合严格 DER，属于解析器过于苛刻，不是令牌无效。绕法：落原始字节，改用项目自己的 `tsa_verify.py`（asn1crypto 系）验。

### 17.2 结果：六家取证、六家验签、四家公共根

| TSA | 端点 | PKI 状态 | 验签 | 链顶 | 公共根 |
|---|---|---|---|---|---|
| DigiCert | `timestamp.digicert.com` | granted | ✅ | DigiCert Trusted Root G4 | ✅ |
| Certum | `time.certum.pl` | granted | ✅ | Certum Trusted Network CA | ✅ |
| **Sectigo** | `timestamp.sectigo.com` | granted | ✅（sha384 摘要、RSA 签名） | USERTrust RSA Certification Authority | ✅ |
| **GlobalSign** | `timestamp.globalsign.com/tsa/r6advanced1` | granted | ✅ | GlobalSign Root CA - R6 | ✅ |
| Apple | `timestamp.apple.com/ts01` | granted | ✅ | Apple 根（不在 certifi） | ❌ |
| freetsa | `freetsa.org/tsr` | granted | ✅ | 社区自签根 | ❌ |

- 同一 sha512 摘要（`196b77c1…738d` = sha512(ROOT.txt)）；两家新令牌 genTime 均为 2026-11-26T13:36Z 段，`imprint_matches_payload=true`、`signature_ok=true`、`chain_verified=true`、`top_in_public_roots=true`。
- `TSA_GUARD.json` 从"4 验签 / 2 公共根"变为 **`verified=6, public=4, level=OK`**；多轨阈值（≥2 达标）现在有 2 倍余量。
- 顺手修了复用逻辑的漏洞：原来只要 `root.tsr` 验签通过就直接复用、不再问新供应商，加了供应商就会"看起来跑了其实没跑"。现在复用条件加了"上一轮已覆盖全部供应商"。

### 17.3 仍是边界

公共根命中只说明"该令牌的链能上溯到浏览器/系统信任的根"，**不等于该 TSA 是 eIDAS 合格信任服务商**，也不产生法律推定。真要法律效力仍得走合格 TSP 或公证，这条没变。

## 十八、连续性：每日心跳与"停更即报红"

竞品在这一维上的说法是"长期有效、持续监控"（OriginStamp 的 proof 长期保管、Bernstein 的版本快照与周期复核）。我们原来的真实短板很直白：整套链只跑了两天，"连续性"没有任何可核的东西。

### 18.1 机制

`heartbeat.py` 每天写一条到 `out/CONTINUITY.jsonl`（只增）：

- 当日快照：文件数、Merkle 根、`ROOT.txt` sha256、日志链头（anchored/current）、台账链头、签名树头 + 主 TSA genTime；
- `prev_entry_hash` + `entry_hash`（后者 = sha256(canonical_json(去掉 entry_hash))），行与行串成哈希链；
- `drift`：若承诺值与上一条不同（换了新证据包），逐字段记下 prev/now，页面明确写"drift 不等于旧承诺失效"；
- 幂等：同一天、同一快照重复跑不写第二条（实测第二次输出 `{"heartbeat":"noop","seq":1}`）。

`summarize()` 同步重算整条链（`chain_valid`）、列出缺口日期（`gaps`），写 `CONTINUITY.json`。页面 `continuity.html` 把汇总、drift、逐日记录、自核方法、边界全摊开。

### 18.2 守门

- 仓内 `scripts/check_continuity.py`：逐行重算 `entry_hash`、校验 `prev_entry_hash` 链接、最近一条日期距今 ≤ 3 天；任一不过即 `结论：FAIL` 退出码 1。
- 已接进 `.github/workflows/verify.yml`（每次 push 必跑）。意义是：**这条链如果哪天没人核了，CI 会自己红**，不靠我口头保证还在跑。

### 18.3 已暴露的自身缺陷（诚实记账）

1. 第一次写的幂等判断有 bug——拿顶层字段去比嵌套的 `snapshot`，结果同一天连写了 4 条重复。已修（改比 `snapshot` 嵌套体），并把历史重复去重、重算哈希链，现有 1 条（2026-11-26，seq=1）。
2. 头两条时间戳相差 6 秒即重复登记，说明"按天去重"必须显式比对快照而不是只比日期。这条已写进代码注释与本节。

### 18.4 与竞品的对照结论

| 维度 | 竞品 | 本项目 |
|---|---|---|
| 长期保管/续期 | 商业服务承诺 SLA | 每日心跳 + 只增哈希链，停更 3 天 CI 报红（自证，不依赖服务商） |
| 版本快照 | Bernstein 按项目版本 | `drift` 字段逐字段记代际变化，旧值不被覆盖 |
| 缺口可见 | 通常是"服务不中断"的隐含承诺 | 缺口日期直接列在公开页，缺就是缺 |

仍然落后：法律推定（eIDAS 合格 TSP / 公证）、真人见证回执（0 条）、商业 SLA 与 UI/API。这三项不是机制能补的，得靠人和资质。

## 十九、零依赖复验入口（对标"一条命令验"）

竞品最强的体验不是"我们公开了"，而是"你一条命令就能验"：Sigstore 是 `cosign verify`，OriginStamp 是取证 API + 证书。我们此前有三条入口，但都带前置条件——`verify_public.ps1` 要 PowerShell + 独立 venv，`verify.html` 要浏览器，`verify_pack.py` 要 cryptography 与 ots。第三方 CI（99% 是 Linux + python3）拿不动。

### 19.1 做了什么

`scripts/verify_min.py`（仅标准库）+ `verify.sh`（POSIX shell 包装），7 项：

| # | 检查 | 依据 |
|---|---|---|
| 1 | `ROOT.txt` sha256 == `index.json.commitments.root_txt_sha256` | 文件与索引互相钉死 |
| 2 | `ROOT.txt` 内 `root` == `index.json.merkle_root` | 根值不自证 |
| 3 | `ROOT.txt` 内 `file_count` == 索引值 | 规模不自证 |
| 4 | 连续性台账逐行重算 + `prev_entry_hash` 链接 | 第十八节机制 |
| 5 | 连续性最近一条距今 ≤ 3 天 | 停更即暴露 |
| 6 | 主张签名 Ed25519（规范字节） | 无 cryptography 时降级 **WARN**，绝不假 PASS |
| 7 | Rekor v1 在线在册（`--offline` 可跳） | 公共日志侧核对 |

设计上刻意踩过两个坑并已修：① 签名文件是 **base64 文本**，按原始字节验会 `InvalidSignature`（改成 `base64.b64decode` 后通过，规范字节 sha256 `e1d07c4dcaff…b3ebb8` 与 Python 侧一致）；② Rekor uuid 不在 `index.json` 而在 `attest/REKOR_PROOF.json`，取错源会误报"没有 uuid"。

### 19.2 实测

- 本仓根：`结论：PASS（7 项通过/警告，0 项失败）`，退出码 0。
- 全新克隆目录（`git clone --depth 1` → 直接跑）：同样 7 项 PASS、退出码 0，无 venv、无 pip。
- 负样本：把 `index.json` 的 `merkle_root` 改成 64 个 0 → 第 2 项 FAIL、`结论：FAIL`、退出码 1。
- 已接进 CI 第 14 步，与 selfcheck、连续性守门并列；三个提交 `997afd0 → 76aabfc` 均 CI success。

### 19.3 仍落后

机器可消费的**在线 API**（HTTP 端点、鉴权、SLA、按次计费）我们没有，也做不了——静态 Pages 只能发文件。我们的等价物是"文件 + 一条命令"，不承诺可用性等级。法律推定与真人见证回执仍是 0，这两项非机制可补。

## 二十、fail-closed 自测与继任预案

竞品的演示几乎都只跑 PASS。真正该被证明的是反面：**篡改之后验证器会不会红**。

### 20.1 五个篡改用例，五个都被抓住

`scripts/selftest_negative.py` 在临时副本上逐项制造篡改，然后用 `verify_min.py` 的检查函数断言对应项必须变 FAIL：

| 篡改 | 命中检查 |
|---|---|
| 改 `index.json` 的 `merkle_root` 为 64 个 0 | `ROOT.txt 内 root == index.json merkle_root` |
| 改 `attest/ROOT.txt` 的 root 行 | `ROOT.txt sha256 == index.json` |
| 改连续性 `entry_hash` | `连续性哈希链可重算` |
| 把连续性台账整体改成 30 天前（哈希链重算自洽） | `连续性未停更（≤ 3 天）` |
| 改 `CLAIM.json` 内容 | `主张签名 Ed25519` |

实测输出 `结论：FAIL_CLOSED_OK（5 个篡改用例）`，退出码 0（表示"篡改都被抓到"，不是"验证通过"）。第四例特意重算了哈希链，专测停更检测而不是哈希检测——否则测的其实是同一件事。已接进 CI 第 15 步。

局限写清楚：自测证明"这些已知篡改会被抓"，不证明"所有篡改都会被抓"。

### 20.2 继任与离场（`SUCCESSION.md`）

- 不依赖我的三样：比特币锚、RFC3161 令牌、主张公钥——都在公共体系里，人走了仍可验。
- 真正会丢的：私钥（只在本机 `.vault/`，无云端副本）与"续跑心跳"的人。
- 交叉签名继任程序已写明（旧钥签继任声明 → 声明哈希再上链/取证 → 新主张引用该声明哈希），**尚未生成继任密钥**：没有真实继任需求时凭空造一把只会扩大泄露面。
- 明确拒绝"私钥托管到云"这种便宜方案：等于把伪造能力交给第三方。

### 20.3 仍落后

在线 API / SLA / 法律推定 / 真人见证回执。前两项受静态托管限制，后两项需要资质与人，不是机制能补的。
